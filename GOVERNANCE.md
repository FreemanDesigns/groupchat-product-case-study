## Publication gate

1. Check the owning records and exact as-of date before changing a status, metric or claim.
2. Confirm no user identity, email, real posts, invite/recovery tokens, passwords, source secrets, private URLs or employer-confidential material are present.
3. Distinguish **planned**, **reported**, **implemented**, **deployed**, **automated tested**, **accepted**, and **measured outcome**.
4. Publish a dated case-study revision here, then reconcile the portfolio summary/links. If a verification cannot be completed, label it pending instead of inferring success.
5. Test public links from a signed-out browser where possible; verify GitHub visibility and the absence of private paths.
6. Record each external update in the [change log](CHANGELOG.md). Do **not** claim automatic synchronization.

## Metric integrity

- Each externally published metric requires a definition, numerator, denominator, date window, segmentation, and source, or an explicit note that these are missing.
- Automated test counts are **not** user conversion, retention, or product success rates.
- Do not call planned instrumentation operational.
- If privacy-safe measurement or validation has not been performed, label the result **Not yet measured**, not zero.

## Release consistency

The public GitHub case study v1.2 describes the **documented beta state through v65**. Sites metadata and the public landing page were reviewed October 30, 2026; the current reported version is 65. Authenticated user journeys were not retested. It does not assert that GitHub contains the deployed app's latest source. Updating the case study does not fix beta defects or close acceptance tickets.

**Reconciliation trigger:** meaningful deployment, verified user acceptance, outcome measurement, portfolio publication, or correction of a material claim.
